Abstract

What this work is, in one paragraph. Phishing and OTP fraud target ordinary office users, while detection tools and security training normally live in separate systems [1]-[4]. This thesis presents FinLearn Guard, a single FastAPI web platform that closes the loop: a threat is detected by an offline rules screener plus a free large-language-model verdict [2]-[4], every connected browser is alerted live over WebSocket, and the Support page immediately explains the fix in text, spoken voice (mp3), and short video (mp4). An endpoint agent extends coverage to real PCs. Measured on the development machine, a phishing sample is judged phishing/high in about one second (rules stage 0.0 ms), a full voice-plus-video guide renders in about six seconds, and an automated suite of three tests passes fully. A survey of 120 recent works on LLM-based phishing detection, agentic AI, personalised security training, and benchmarks positions the work and identifies its research gap: detectors rarely teach [2][3][13], trainers rarely detect live [31]-[36], and few designs ship as one runnable system [37]-[43].

Chapter 1: Introduction (briefed)

1.1 Background - what problem exists

Electronic communication is the primary attack surface for fraud against finance and office staff: forged login pages, urgent OTP requests, and fake invoices. Technical filters stop part of this traffic, but the remainder reaches humans, who remain the decisive line of defence. Daily volume is massive - billions of spam mails per day [4] - and small wording changes evade signature gateways, which motivates semantic defences that understand language, not just match strings.

Example. "Dear customer, your account will be suspended in 2 hours. Verify now at http://bit.ly/otp-login with your OTP." A keyword filter sees "verify" and "http" but cannot tell urgency + credential request + short-link together mean danger. Our system scores each clue and asks an LLM to read intent [1][2].

1.2 Motivation - why detection and training must join

Detection systems raise alerts that non-expert users cannot interpret, while training material is static and disconnected from live incidents. Recent literature shows both halves advancing separately - LLM-based detectors on one side [1]-[4][23]-[30] and personalised, event-triggered training on the other [6]-[8][31]-[36] - but deployable systems combining them in one loop are rare [13][37]-[43]. Field studies show personalised, in-workflow lessons outperform generic slides [6][9][94]-[99], and embedded training works through timely nudges, not long content [101][103]. This thesis builds that combination at student scale, using only free tools.

1.3 Problem Statement

How can a small organization detect phishing-like threats and immediately teach each affected user the correct response, inside one maintainable web system, without paid services? Sub-questions: (a) how to detect 7 finance-text attack classes in ~1 s without a GPU; (b) how to push the verdict to every screen without refresh; (c) how to turn the same verdict into steps + voice + video that a clerk can follow; (d) how to prove it with tables, not claims.

1.4 Objectives - what the system must do (briefed)

  • O1 Serve one server. Pages, JSON APIs, realtime alerts, and media from one FastAPI app, so a student can run and demo it on one port.
  • O2 Detect hybrid. Instant offline rules plus a free AI verdict, with a deterministic safety override (score >=0.6 can never be "safe") [25][69][70].
  • O3 Alert live. All browsers update without refresh via WebSocket.
  • O4 Guide in 3 formats. Steps, voice (edge-tts mp3), video (moviepy mp4) from the same diagnosis, self-actionable only (no "call IT").
  • O5 Cover real PCs. Zero-install endpoint agent (stdlib only) for heartbeats and burst alerts.
  • O6 Fail honestly. Clear errors, never fabricated answers; missing key returns verdict=error.

1.5 Scope (in / out)

Prototype scope: phishing/OTP-style text threats, English language, single-server deployment, free-tier cloud services. Seven text classes: phishing, otp, bec, sqli, xss, malware, safe. Out of scope: raw packet sniffing, multilingual guides, and longitudinal user studies (protocol only, see EVAL_B_PACK). Packet agents [58][62] and avatar video are explicitly deferred and disclosed as limits.

1.6 Contributions

  • C1 Closed-loop design: one JSON shape, one DB, one server linking detect -> push -> teach -> store.
  • C2 Safety-locked hybrid detector (rules + frozen LLM, no training, reproducible).
  • C3 Four-agent orchestration (detector / alerter / support + endpoint) over REST + WebSocket with 5-step trace.
  • C4 Honest evals: Eval-A 70 live + Eval-Big 1995 harness + N=30 human protocol, synthetic limits disclosed.

Chapter 2: Literature Review (120 works)

Method. We group 2024-2026 literature into six pillars: (A) agentic/multi-agent fraud & finance, (B) LLM phishing detection, (C) personalised tutoring, (D) benchmarks & safety, (E) agent orchestration & systems, (F) web/DB/media engineering. Full list is in References [1]-[122]. Below we brief each pillar: what it proves, what it lacks, and what we borrow.

2.1 Pillar A - Agentic and multi-agent fraud & finance (closest rivals)

Multi-agent LLM systems now split fraud work across roles: SAGE uses profile/plan/optimize agents and lifts F1 by 40.86% [13]; risk-first evaluation shows single-task scores hide team risk [14]; AMLNet pairs generation with detection [15]; AuditAgent chains evidence across documents [16][76]; AgenticCyber fuses log+vision+audio at 96.2% F1 in 420 ms [17]; MALCDF runs 4 SOC agents on LLaMA-3.3-70B [18]; Hmimou et al. combine email+log+IP agents with RAG [19]; CyLens scales to 271k threat reports [20]; TradingAgents/FinCon/HedgeAgents/FinRobot show finance agent debate, hierarchy, and scheduling patterns we reuse [21][70]-[75]. Real-time payments defence adds triage/investigator/response layers [22]. Tool-using agents can already hack websites and exploit one-day CVEs in the lab [55][56], which justifies a fast detector-to-alert path before compromise. Local 7B agents can match GPT-4 on narrow tasks [58], and reasoning/generation/parsing splits [57], IDS-agent pipelines [59], explainer overlays [60], CTI-grounded response [61], CAGE-4 team protocols [62], SOC triage under 10 min [63], and staged URL->screenshot->HTML cascades at $3.18/1k sites [68] all inform our 3+1 agent split. Finance analogues (anomaly research agents [70], FinAgent tools+reflection [71], FinCon verbal RL [72], TradingAgents debate [73], HedgeAgents conferences [74], FinRobot scheduler [75], AuditAgent evidence chains [76], collusion warnings [77], e-commerce MDP rewards [78], AutoGen conversation control [79]) converge: agents help, but none ships detection + live push + teaching in one student-runnable server.

2.2 Pillar B - LLM phishing and fraud detection (our detector layer)

LLMs both create and catch phishing: GPT-4 lowers attacker cost yet also detects intent, sometimes surpassing humans [1][104]; ChatSpamDetector reaches 99.70% with reasons [2][53]; APOLLO reaches 97.4% alone and 99% with URL enrichment, with warnings users trust more than browser chrome [3][57]; PhishEmailLLM meta-models approach 99% at lower cost [4]; classical ML (Random Forest 99.47% on 26,365 mails) is cheap but brittle on paraphrase/HTML/multilingual [5]; RAG personalization cuts false positives by 66.7% to F1 0.9703 [23][65]; memory-augmented multimodal agents beat static workflows [24]; prompt-injection still breaks 10-40% of detectors, which justifies a rules safety-lock [25][69][70]; screenshot+temp-0+commercial-model recipes [26], cost-optimized recall +40% [27][68], early personalization evidence [28], tabular-vs-LLM honesty (XGBoost 98.48% beats LLMs on IEEE-CIS) [29][107], and tabular-to-text RAG [30] shape our limits. Adversarial and multimodal extensions - debate judges [59], rephrase evasion [60], brand-ID checks [61], knowledge-graph brands [62], single-iteration online+offline agents [63], PhishOracle harnesses [64], client-side MobileBERT [65], one-shot URL CoT [66], Korean smishing <5B models [67], SmishX 98.8% + N=175 study [68], Mixtral SMS 98.6% [69], on-device 3.46 MB pipelines [70], campaign clustering [71], persuasion augmentation +5.3% [72], Mozambican mobile-money sets [73], BEC reviews finding only 2/30 human-in-loop hybrids [74], structured-query defences [75], instruction hierarchies [76], and prompt-vs-finetune comparisons [77] - collectively argue for frozen LLM + deterministic rules + explicit override rather than trusting either stage alone.

2.3 Pillar C - Personalised tutoring and cyber education (our support layer)

Tutoring works when it is timely, stepwise, and matched to proficiency. LLM tutors with transparent feedback anchor the field [31][78]; multi-LLM detect-understand-remediate loops mirror our pipeline [32][79]; injecting flaws into the student's own code (N=71) is the strongest personalization precedent [33][80]; curriculum mapping [34], 24/7 RAG mentors [35], and KG-grounded QA [36] add coverage. Learning science agrees: ChatGPT hints can equal human hints in RCTs (N=274) [94]; live-tutor copilots lift mastery +4pp across 1,800 students [95]; pedagogical AI tutors double learning in less time [96]; two-year school trials warn engagement is the bottleneck [97]; in-field prompting RCTs give a reusable pre/post protocol [98]; step-explanations beat answers alone and Socratic style engages [99]; role-play improves reporting in N=105 + 3 live tests [100]; embedded training works via nudges [101]; proficiency matching levels the field (N=342) [6][102]; LLM-generated landing pages enable per-user lessons [103][16]; phishing codebooks structure curricula [105]; and AI training shows pre-post gains even with simple prompts (N=480) [10]. What is missing: none of these tutors takes a live detection feed as input. Our Support agent does.

2.4 Pillar D - Benchmarks, safety, and human-study methods (our eval layer)

Benchmarks set the bar but build no loop: Fraud-R1 (8,564 multi-round cases) [37][69]; MultiAgentFraudBench (28 lifecycle scenarios, collusion risk) [38][77]; FinSafetyBench (bilingual refusal) [39]; XFinBench (4,235 grad-finance Qs) [40]; FinBen (42 datasets/24 tasks) [41][85]; Finance Agent Benchmark (537 SEC tasks, o3 only 46.8%) [42][86]; InvestorBench trading decisions [43]; FinQA reflection +15% [87]; multi-turn fraud robustness [88]; multimodal page agents [89]; CTF stepwise scoring [90]; CyberSecEval 2/3 (injection, abuse, social-engineering scale) [91][92]; AgentHarm (110 malicious agent tasks) [93]; HarmBench (510 behaviors) [94]; SWE-bench fix methodology [95]; AgentBench multi-turn decisions [96]; SWE-agent guardrailed tools [97]. Our Eval-A (70, 7 kinds), Eval-Big (1,995 harness), and Eval-B N=30 protocol (EVAL_B_PACK) follow these methods at student scale, with synthetic limits disclosed and public-data swap prescribed before any Q1 learning claim.

2.5 Pillars E-F - Orchestration, web, and engineering foundations

Our orchestration follows proven patterns: conversable multi-agent control [79], provider registries and lifecycle guards [65], self-reflective orchestrator/deflector/responder loops [66], and incident DSLs [67]. Web/engineering choices are deliberately boring: FastAPI + Uvicorn + Jinja2 + WebSocket (RFC 6455) + StaticFiles [106]-[109], MongoDB Atlas dual-backend [110], edge-tts [111], moviepy + imageio-ffmpeg [112], httpx gateway [113], pytest [114], Docker/Render/Procfile deploy [115], OWASP Top-10 and NIST guidance for threat classes [116][117], and Python stdlib (netstat/ipconfig) for the endpoint agent [118]. Boring is a feature: one server, one DB, reproducible.

Three collections: employees(id, name, risk), threat_events(id, title, kind, severity, ts), devices(id, ip, conns, last_seen). One schema in code runs on both SQLite (local) and MongoDB Atlas (cloud) so class demo and Render deploy share logic.

3.6 Closed-loop workflow - worked example (briefed)

Input: title="Urgent: verify your account", body="suspended in 2h, login at http://bit.ly/otp-login with OTP". Step 1 Rules finds verify(0.35)+otp(0.30)+urgent(0.20)+http(0.20)=1.0. Step 2 LLM returns {"kind":"otp","verdict":"phishing","severity":"high"}. Step 3 Safety-lock holds (1.0>=0.6, stays phishing/high). Step 4 Alerter saves event, bumps employee to high, broadcasts WS. 4.1 Overview - why agents (briefed)

An agent senses, decides, and acts without a human clicking each step [55][62][79]. We use four small agents instead of one big function so each can be tested, timed, and replaced: two decide (detector, support), one persists/notifies (alerter), one senses PCs (endpoint). They communicate only through typed dicts + REST + WebSocket - never shared globals - following conversable-agent [79], registry [65], and reflection [66] patterns at student scale (no RL, no auto-evolution).

4.3 What is your model - specification (briefed)

Short answer for the supervisor: there is no trained neural model in this thesis. The "model" is a hybrid decision procedure: (i) a 14-row weighted regex scorer (deterministic, 0.0 ms, offline), plus (ii) a frozen commercial LLM called through one gateway (OpenRouter, default mistralai/ministral-8b-2512 via OPENROUTER_MODEL), constrained by (iii) two deterministic locks. No fine-tuning, no embeddings trained, no gradient updates. The Eval-Big "ML centroid 1.000" is a harness check on synthetic slot-fill data, not a deployed model - disclosed as overfit by design.

5.2 Detection algorithm (briefed with trace)

Eight lure families map to 14 rows (Section 4.3). Matches sum weights, cap 1.0. LLM returns kind/verdict/severity/reason JSON. Override forces phishing/high when score>=0.6. Trace for the running example: Received (0.0ms) -> Rules screener signals=verify,otp,urgent,http score=1.0 (0.0ms) -> AI verdict otp/phishing/high "OTP lure with short link" (~1100ms) -> Handling saved id + risk E001->high + broadcast (~5ms) -> Done total ~1300ms. The dashboard inspector renders exactly these 5 rows with red <mark> on "verify/OTP/http", a danger meter at 100%, and severity badge HIGH.

5.3 Support pipeline (briefed with example)

Question -> rules signals + detector context -> support prompt -> problem/severity/steps/voice_script -> scrub replaces deflecting steps with self-actions from per-kind pools -> mp3 + mp4 rendered and cached -> answer broadcast. Example: Q "OTP on WhatsApp, should I share?" -> kind=otp -> steps: never share OTP / call back official number / block caller / enable 2FA -> voice_script spoken via edge-tts -> 4 slide cards via moviepy. If moviepy missing, honest "Video needs moviepy" card appears (later fixed by installing moviepy + imageio-ffmpeg).

5.4 User interface (briefed)

Dark gradient theme, sticky topbar with LIVE pill, hero, live feed with clickable rows, 5-step inspector with animated meter, twin graphs (attacks/min + perf), employee table, tabbed Support answer (Steps/Voice/Video), device board. Zero emoji; CSS sections 0-11 labeled. Players use controlsList="nodownload" + no-context-menu so users listen/watch instead of downloading.

Chapter 7: Conclusion and Future Work

This thesis delivered a running closed-loop platform: detection and guided response in one server, built only with free tools, verified by passing tests and live measurement. It demonstrates that the literature's two advancing fronts - LLM detection [1]-[4] and adaptive training [6][10] - can be fused into a single teachable system orchestrated as four small agents. Future: true packet-level agent [58][62], risk auto-update from guide completion, multilingual voice, admin analytics, and a controlled user study (pre/post accuracy) following [6][10][98][100]; public-data eval swap [29][37]; cost/latency cascade [68]; safety red-teaming [91]-[94] before any classroom deployment.
